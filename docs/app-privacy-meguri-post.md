# 巡り便（Meguri Post）の App Privacy 申告表

App Store Connect の「App のプライバシー」で、5.0.0（巡り便の追加）の提出時に申告する内容の下書き。
巡り便を追加すると、これまでの「データの収集なし」から変更が必要になる。

根拠は `privacy.html` の「07 巡り便を使う場合」。内容を変えるときは両方をそろえること。

## 申告する項目

| Apple の分類 | 該当するデータ | 目的 | ユーザーに紐づくか | トラッキング |
|---|---|---|---|---|
| User Content → Photos or Videos | 巡り便に付けた写真（記帳に追加した写真から、お店ごとに任意で1枚まで。撮影場所などの情報は削除済み） | App Functionality | はい（下記の注1） | いいえ |
| User Content → Other User Content | 題、店名・ジャンル・所在地、推し度（自分の言葉で書いた場合はその言葉を含む）、予算感、ひとこと、差出人の地域（都道府県か地方の名前。「愛知県のだれか」などと表示）、返事スタンプ、通報の理由、差出人のブロックの記録 | App Functionality | はい（注1） | いいえ |
| Identifiers → User ID | 巡り便を初めて使うときに作られるランダムな識別番号（Supabase の匿名サインイン、注2） | App Functionality | はい（注1） | いいえ |

- どの項目も、広告・分析・トラッキングには使わない。
- 「目的」は App Functionality（投稿の確認と配信、1日の件数の上限、同じ便を2回届けない、返事の配信、取り下げ、通報と投稿の停止、ブロックした差出人の便を届けない）のみ。
- 「どの便をどの識別番号に届けたか」の記録は、同じ便を2回届けないためだけに使う。App Functionality の範囲として扱い、Usage Data には含めない。
- 受け取る便を「集めているジャンルだけ」に絞っているときに送るジャンルの一覧は、届ける便をその場で選ぶためだけに使い、サーバーに保存しない。Apple の定義では「収集」に当たらない（その場の要求に応えるためだけに使い、残さないデータ）ので、App Privacy の項目には足さない。プライバシーポリシーには「送信される情報」として書く。

### 注1：「ユーザーに紐づく」を「はい」にする理由

氏名や Apple ID とは結びつかないが、投稿・返事・通報は識別番号とひも付けて保存し、
それを使って本人の取り下げや、悪質な投稿の停止を行う。
Apple の定義では「端末」にひも付く場合も「紐づく」に当たりうるため、安全側で「はい」とする。

### 注2：Device ID ではなく User ID にする理由

Apple の Device ID は「広告識別子など端末単位の ID」を指す。
アプリが自分で割り当てるランダムな ID は User ID（assigned user ID）の方が実態に近い。
どちらで申告しても審査上の問題は出にくいが、判断の根拠としてここに残す。

## 申告しない項目（判断メモ）

| 候補 | 申告しない理由 | 再検討が必要になる条件 |
|---|---|---|
| Location（Precise / Coarse） | 送るのは「お店の所在地」で、利用者や端末の位置ではない。差出人の表示もお店の所在地から決める | 利用者の現在地を送る、または現在地から差出人の表示を決めるように変えた場合 |
| Usage Data | 返事スタンプは利用者が書いた内容の一部として Other User Content に含めた | 閲覧回数や開封の記録など、操作の記録を集めるようにした場合 |
| Diagnostics | クラッシュ収集・解析ツールを入れていない | それらのツールを入れた場合 |
| Contact Info / Name / Email | 集めていない。メールでの削除依頼は巡り便の機能の外で、アプリが集めるデータではない | アプリ内に問い合わせフォームを付けた場合 |

**判断が分かれうる点**：Location を申告しない判断は、「お店の所在地は利用者の位置ではない」という解釈に基づく。
ただし、巡り便に選んだお店の分布から利用者の生活圏が推測されうるため、
より慎重にするなら Coarse Location（App Functionality、紐づく、トラッキングなし）を申告する選択肢もある。
申告しすぎて審査で不利になることは基本的に無い。

## あわせて App Store Connect で変えるもの

- **年齢制限の質問**：「ユーザー生成コンテンツ」への回答が変わる。
- **審査用のメモ**：Guideline 1.2 への対応として、以下を書く。
  - 投稿はすべて開発者が確認し、承認したものだけを配信する
  - 受け取り画面に通報ボタンがある。通報された便はいったん非公開にして開発者が確認する
  - 悪質な利用者（識別番号）からの投稿を止められる
  - 受け取った人が、差出人をブロックできる（以後その差出人の便は届かない）
  - 巡り便を初めて使うとき（出す・受け取るのどちらでも）に利用規約（meguri-post-terms.html）への同意を求める
  - 問い合わせ先
- **プライバシーポリシーの URL**：変わらない（privacy.html）。公開は 5.0.0 のリリースに合わせる。

## 実装側で守ること（ポリシーに書いた約束）

- 写真は送信前に端末内で撮影場所などの情報を削除する（EXIFStripper）。写真はお店ごとに1枚まで
- 現在地は送らない。差出人の表示はお店の所在地から決める
- 識別番号は Supabase の匿名サインイン（signInAnonymously）で作るランダムな値。IDFA や端末名は使わない
- サインインの情報は Keychain に保存する（UserDefaults だとアプリを入れ直すだけで投稿の停止を回避できるため）
- アプリ内から自分の巡り便を取り下げられる。取り下げたものはサーバーから削除する
- 取り下げられないとき用に、アプリ内で自分の巡り便の「題」と「投稿した日」が見られること（メールでの削除依頼で使う）
- 通報された便は自動でいったん非公開にする
- 受け取った便の画面から差出人をブロックできる。ブロックの記録はアプリに返さない
- 取り下げたときは、その便への返事と受け取りの記録もあわせて削除する
- 通報されて確認中の便は、確認が終わるまで取り下げられない
- 1日の件数を数える記録（識別番号と日付）は翌日を過ぎたら消す
- 受け取った人に写真のパスや差出人の識別番号を渡さない（写真は期限付き URL で見せる）
- 却下したもの、通報を受けて確認した結果非公開のままとしたものは、その日から90日以内に削除する（定期的に消す仕組みが必要）
- 巡り便を初めて使うとき（出す・受け取るのどちらでも）に規約への同意を求める
- ポリシーを変えたときにアプリ内でお知らせする仕組みを用意する（ポリシーと規約でそう約束している）
